# S3 Storage Migration

Status: planned for **2.3**. Not part of the 2.2 release.

## Goal

Move file storage to an S3-compatible provider without changing user-facing URLs or breaking existing files, while keeping Appwrite usable as a provider.

## What Appwrite 2.0's S3 support actually is

Appwrite 2.0 exposes an S3-compatible **API gateway in front of Appwrite Storage**. It is not an S3 backend: buckets map 1:1, object keys are file names, "folders" are prefixes, ACLs are canned, and access is API-key scoped.

- For the Appwrite path, use the native Storage SDK, not the S3 API.
- Direct S3 means AWS S3, Cloudflare R2, Backblaze B2, or MinIO.
- Self-hosted `_APP_STORAGE_DEVICE=s3` is a separate deployment decision and is not available on Appwrite Cloud.

## Current inventory

Eight active buckets:

`avatars`, `images`, `emojis`, `profile-backgrounds`, `avatar-frames-predefined`, `gifs`, `stickers`, `files`.

`APPWRITE_AVATAR_FRAMES_BUCKET_ID=avatar-frames` in `.env.local.example` is stale and unused; the active bucket is `avatar-frames-predefined`.

## Design

### Provider abstraction

A server-only `StorageProvider` with `appwrite` and `s3` implementations, selected by `STORAGE_PROVIDER`. The provider owns create/delete/read/URL generation, plus list/copy for migration.

### Bucket layout

One bucket. Keys are `{prefix}/{fileId}`:

- `avatars/`
- `images/`
- `emojis/`
- `profile-backgrounds/`
- `avatar-frames-predefined/`
- `gifs/`
- `stickers/`
- `files/` (attachments)

`fileId` is the existing Appwrite file ID for migrated files and `crypto.randomUUID()` for new files. Never hash or append the original filename. Store the original filename and content type in object metadata; set `Content-Disposition` for downloads. S3 "folders" are just prefixes, so duplicate names across prefixes are fine.

### Access control

- **Public read:** `avatars/`, `profile-backgrounds/`, `emojis/`, `images/`, `gifs/`, `stickers/`, `avatar-frames-predefined/` (matches the current `Role.any()` reads).
- **Private:** `files/` attachments. Authorize by message/channel/DM access on the server, then return a short-lived presigned GET or proxy the stream. Do not make the bucket public.
- **Uploads:** validate size and MIME on the server; S3 enforces neither.
- **Deletes:** server-authorized only; never ship delete credentials to clients.

### URLs

Centralize URL building in one module. Public files get a stable URL (custom domain or `/api/storage/...`). Private files get a presigned URL or a server route. Prefer storing file IDs and deriving URLs; migrate existing `fileUrl`, `downloadUrl`, `imageUrl`, and conversation `avatarUrl` values, or map them at read time.

### Client

Server-side `@aws-sdk/client-s3` plus `@aws-sdk/s3-request-presigner`. Use multipart upload from disk for the 50MB attachment path. No mobile S3 client: mobile keeps calling the web API and receives stable or presigned URLs. A workspace package is optional later.

## Migration

1. Add the provider abstraction behind `STORAGE_PROVIDER=appwrite`; no behavior change.
2. Add the S3 implementation and a copy script: list Appwrite files, copy to `{prefix}/{fileId}`, verify size/checksum, write a manifest. Idempotent; skip existing keys.
3. Dual-read: try S3, fall back to Appwrite for missing keys; optionally copy lazily on read.
4. Switch writes to S3. Keep Appwrite files for rollback.
5. Update URL builders and stored URLs. Remove the Appwrite provider after a release.

## Rollout notes

- R2 (10GB free, no egress) or B2 are better defaults than AWS's time-limited free tier.
- Appwrite's S3 gateway has no server-side encryption; R2/AWS do.
- Test range requests (audio/video), large uploads, unicode filenames, and orphan cleanup.
- Keep Appwrite Storage as a provider so self-hosted/Appwrite users are not forced to migrate.

## Out of scope

- Direct browser/mobile uploads; can be added later with presigned PUT.
- Image previews/resizing; the app currently uses `/view`, not `getFilePreview`.
- Per-file ACLs; authorization stays server-side.
